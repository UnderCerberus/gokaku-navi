# 端末内ニューラル翻訳（FuguMT）の試験（2026-10-17）

和訳ツールの長文の誤りを減らす候補として、無料で公開されている英日翻訳モデル FuguMT（[staka/fugumt-en-ja](https://huggingface.co/staka/fugumt-en-ja)、CC BY-SA 4.0）を、未見文の第 29〜42 群（入試長文に近い自作の段落、14 群 420 文）で試した。結果を受けて、和訳ツールに「AI 訳」（任意・初回だけモデルを取得）として組み込んだ（下の「アプリでの動作」）。

## 動かし方

- モデル: [Kadonox/fugumt-en-ja-onnx](https://huggingface.co/Kadonox/fugumt-en-ja-onnx) の量子化版（エンコーダー 36MB・デコーダー 109MB）
- 実行: `tools/nmt/trb.js`（onnxruntime-node を直接呼ぶ。SentencePiece の分割は `tools/nmt/spm.js` で自前に行い、ビーム探索 12 本）
- transformers.js 4.3.1 の `pipeline('translation')` は使えない。理由は 2 つ。
  1. トークナイザーの分割が SentencePiece と違う（wallet → `wall|et` になり「壁」と訳す）
  2. `num_beams` を指定しても先頭の 1 候補しか使わない（実質は貪欲探索）

  この 2 つを直すと、同じモデルでも訳が大きく変わった（例: 「電車で散策した」→「財布を列車に置き忘れた」）
- 速度: CPU（Node）で 1 文あたり平均 0.75〜1.0 秒（ビーム 12）

## ビーム 4 本（アプリの既定）

ビーム 12 本と訳が違った 232 文だけを採点し直した。直ったのは 16 文、悪くなったのは 20 文で、不合格は 153 / 420（36%）、× は 73（17%）。ビーム 12 本（149 文・66 文）とほぼ同じなので、2 倍速いビーム 4 本をアプリの既定にした。

## アプリでの動作（2026-10-17、`js/english/nmt.js`）

- 「AI 訳を使う」を有効にしたときだけ、モデルを Hugging Face から取得する（版を固定し、SHA-256 を照合）。保存先は IndexedDB
- 実行は ONNX Runtime Web（wasm、1 スレッド）を Web Worker の中で動かす。`js/vendor/ort/` の 2 本は `tools/nmt/build-vendor.js` で作る（file:// でも読めるよう、通常の script にした文字列と base64）
- 計測は Chromium 152・http://localhost。モデル取得は約 10 秒、起動は約 4 秒（2 回目以降は IndexedDB から読む）。1 文あたりの訳出は、貪欲探索で約 1.1 秒、ビーム 4 本で約 2 秒。8 文の段落は約 19 秒で、訳せた文から順に表示する
- 完全一致の文（内蔵長文の人手の訳）には使わない
- file:// で直接開いた場合は未確認（確認に使ったブラウザ枠が file:// を静的に表示するだけだったため）

## FuguMT の誤りの型

- 多義語の取り違え: relief → 救援、treat → 治療、trunk → トランク、film → 映画、migration → 移民、shade → 色合い、lost-and-found → 失われた
- 語彙に無い字が `<unk>` になる（10 文: 惰・餃・嫉妬・吠・鳩・桟など）
- 節の脱落（which 節・although 節・and 以下が丸ごと落ちる）と、言っていないことの付け足し（「同社」）
- 熟語の直訳: go out of one's way → 道を出て行った、get off to a great start → スタートに降りて、take their toll → 料金を負担
- 物語・会話の段落（第 42 群のリレーの物語など）で特に崩れやすい
